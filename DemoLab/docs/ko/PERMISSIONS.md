# 촬영 권한

실제 촬영에서 쓰는 실행 경로로 권한을 확인해요. 녹화기 사전 검사만으로 Tatami의 타일링·미러 권한을 증명할 수는 없어요.

|프로세스|필요한 기능|검증 자료|
| --- | --- | --- |
|Tatami|손쉬운 사용: 실제 창 이동과 포커스|보이는 작업 공간 전환과 배치 검증|
|Tatami|화면 기록: 항상 위 미러|확대한 창 위에서도 보이는 공용 상태 창|
|democtl / 실행기|손쉬운 사용: 키보드·포인터·네이티브 컨트롤|실제 입력과 컨트롤 값 검증|
|DemoRecorder / 실행기|화면 기록: 화면 캡처|첫 인코딩 프레임·완성 영상·전체 디코딩 검사|

**전용 녹화 VM**의 시스템 설정 → 개인정보 보호 및 보안에서 필요한 권한을 주세요. 변경 후 프로세스를 다시 실행하고 `democtl doctor`과 짧은 촬영으로 확인하세요. 호스트의 권한이나 개인 Tatami 설정은 바꾸지 않아요.

`record start`은 호출자에게 캡처 권한이 있으면 직접 실행하고, 없으면 LaunchServices를 써요. 현재 게스트의 `tart exec`은 미리 허용된 에이전트를 통해 실행돼요. 이 이미지와 경로에서 확인한 결과일 뿐, 모든 게스트나 재빌드 파일에 적용되는 약속은 아니에요.

<a id="a-window-can-outlive-the-process-that-requested-it"></a>
## 요청한 앱이 꺼져도 권한 창이 남을 수 있어요.

예전 종합 영상에는 **Tatami** 권한을 요청하는 `Screen Recording` 창이 남아 있었어요. 앱 창 뒤에 가려졌다가 창을 닫으면서 나타났고, 녹화기만 검사하던 방식은 놓쳤어요. 정기적인 녹화 알림이라는 증거는 아니었어요.

다른 앱 뒤에 가려져 있어도 권한·설정 창이 있으면 거부해요. 게스트에서 해결하고 다시 시도하세요. 오래된 요청을 닫는 것과 권한을 주는 것은 달라요. 실제 권한이 없다면 시스템 설정에서 허용하고 관련 동작을 확인해요.

`democtl record warmup`은 녹화기만 확인해요. Tatami의 별도 캡처 경로는 `shared`도 연습해서 확인해야 해요. 권한 창을 잘라내거나 미검증 영상을 성공으로 표시하지 마세요.

<a id="repeatable-recording-image"></a>
## 다시 쓸 수 있는 녹화 이미지

정확한 도구와 앱을 빌드하고 권한·실제 작업을 확인한 뒤 VM 이미지를 보관하세요. 재빌드나 실행기 변경은 권한 귀속을 바꿀 수 있어 다시 확인해야 해요. DB 행을 복사하거나 예전 권한을 가정하지 않아요. TCC DB를 직접 고치던 스크립트는 삭제했어요.
